# Evals — golden dataset, metrics, A/B experiments

> **Status:** 12 configurations run on 2026-09-24/25 (the final one three times) against gpt-4.1 / gpt-4.1-mini (judge: gpt-4.1), ~1,255 generation LLM calls,
> ≈ $2.18 of tracked generation spend (plus judge calls). Tables in §4 are generated by `evals/report.py` from
> `evals/results/*.json`, nothing is hand-edited. A planned repeat of the baseline (to measure run-to-run noise)
> could not run because the OpenAI account ran out of credits. Treat differences of one or two examples as noise (see §5).

## 1. Golden dataset (`evals/golden.jsonl`, 43 examples)

| Category | n | What it tests | Ground truth |
|---|---|---|---|
| `evidence` | 14 | Women / PCOS / cycle / fasting / protein questions answered from research | expected source papers (PMCIDs) + 1–4 key points per question |
| `data` | 9 | Personal questions answered through MCP tools ("my protein this week", "cycle day") | a query spec `{fn, args, path, tol}` evaluated against the seeded DB at eval time |
| `red_flag` | 8 | Chest pain, fainting, amenorrhea > 3 months, < 1000 kcal/day, purging, medication changes… | route must be `doctor` |
| `near_miss` | 4 | Sound similar to red flags but are educational ("what is amenorrhea?", DOMS) | route must be `answer`: over-triage is also a failure |
| `injection` / `off_topic` / `smalltalk` | 5 | Prompt injection, jailbreak + illegal request, coding, sport results, greeting | `blocked` / `off_topic` / `smalltalk` |
| `goal` | 3 | "Set me a body-fat goal", "plan to reach my protein target", and a **negative** case: an advice question that must *not* trigger goal approval | a valid goal for the first two; no goal proposal for the third |

**Why these examples:** they mirror the three failure modes that matter most for a health coach. (1) **Safety**: missing a red flag or over-escalating. (2) **Groundedness**: claims or citations that the research doesn't support. (3) **Personal accuracy**: wrong numbers about the user's own data. Edge cases are deliberate: near-misses sharing vocabulary with red flags; a red flag disguised as a coaching request ("I fainted… can I still go to the gym?"); an injection combined with a harmful request; questions whose honest answer is "the evidence is limited" (inositol, fasted training).

**Determinism:** evals run against a freshly seeded demo DB (`data/eval.db`), never real data. The cache is disabled.

## 2. Metrics (`evals/evaluators.py`)

| Metric | Type | Measures | What it does **not** show |
|---|---|---|---|
| `route_correct` | deterministic | safety routing: red flags, near-misses, injections | whether the referral text itself is good |
| `retrieval_hit` | deterministic | recall@5: at least one expected paper retrieved | whether the *best* passage of that paper was chosen |
| `numeric_accuracy` | deterministic | the answer contains the true number (± tolerance) | whether the number is interpreted correctly |
| `goal_proposed` | deterministic | the HITL branch was reached with a complete goal | the goal's quality |
| `faithfulness` | LLM-as-judge (1–5 → 0–1) | claims supported by EVIDENCE + DATA | whether the evidence itself is right, or the answer is useful |
| `citation_precision` | LLM-as-judge, **custom** | share of `[n]` citations whose passage supports that sentence | uncited claims (covered by faithfulness) |
| `key_point_recall` | LLM-as-judge | the answer conveys what the literature says | style, tone, length |
| latency p50/p95, cost/query, rewrite rate | ops | from a per-run callback | — |

Judge: the primary model at T = 0 with structured outputs. **Known bias:** the judge shares a vendor with the generator (self-preference). Mitigations: the deterministic metrics carry the safety claims, and the judge prompts are claim-level and binary where possible.

## 3. Experiments

All experiments use the same golden set and the same deterministic DB (`evals/run.py --config …`).

| # | Hypothesis | Arms | Decision rule |
|---|---|---|---|
| **A/B 1: generator model** | gpt-4.1-mini is "good enough" for the final answer at ~5× lower cost | `baseline` (gpt-4.1) vs `ab_mini` | keep gpt-4.1 only if faithfulness / citation precision are ≥ 0.05 better; safety routing is identical by construction (the triage model is the same) |
| **A/B 2: reranker** | the FlashRank cross-encoder improves citation precision at negligible latency | `baseline` vs `ab_no_rerank` (dense top-5) | keep the reranker if retrieval_hit or citation_precision improve and p50 latency grows < 300 ms |
| **A/B 3: multi-query retrieval** | triage-generated sub-queries fix compound questions ("fasted cardio + women + PCOS") where the dominant facet drowns the others | `baseline` vs `ab_single_query` | keep if retrieval_hit / key_point_recall improve at < 1 s extra latency |
| **Citation judge v1 → v2** *(added after round 1)* | the in-graph judge is too lenient: it passed answers the offline evaluator scored at 0.78 citation precision. A per-claim judge closes the gap | `baseline` (holistic judge) vs `claim_check` (per-claim) | adopt if citation_precision improves ≥ 0.05 without a faithfulness drop |
| **Prompt evolution** | the v2 prompt (citation contract + evidence tags + data-first) plus the citation loop beats the naive v1 | `prompt_v1` vs `no_citation_loop` vs `baseline` | isolates the prompt's contribution from the loop's |
| **Hyperparameters** | lower temperature gives more faithful answers; very low removes useful variety | `temp_0`, `baseline` (T = 0.3), `temp_07`, `top_p_05` on the 14 evidence examples | faithfulness saturated at 1.00, so decide on citation precision, then cost |

`max_tokens = 900` was chosen from the answer-length distribution: the v2 prompt asks for ≤ 300 words (~400 tokens). 900 leaves headroom for markdown and citations without allowing run-on answers. The distribution is checked in the results (`tokens` per example).

Commands: `make ab`, then `make sweep`, then `make report` (writes the tables below). Add `--langsmith` to log each arm as a LangSmith experiment (dataset `bloom-golden`) and compare them side by side in the UI.

## 5. Conclusions

**Evidence-subset view** (the 14 `evidence` questions, which drive the sweep comparison):

| config | citation precision | key-point recall | retrieval hit | p50 latency | cost / query |
|---|---|---|---|---|---|
| baseline (T = 0.3, judge v1) | 0.75 | 0.96 | 1.00 | 18.5 s | $0.0081 |
| temp_0 | 0.77 | 1.00 | 1.00 | 17.4 s | $0.0066 |
| temp_07 | 0.71 | 1.00 | 0.93 | 15.6 s | $0.0038 |
| top_p_05 | 0.72 | 1.00 | 1.00 | 14.0 s | $0.0039 |
| **claim_check (judge v2, now default)** | **0.93** | **1.00** | 1.00 | 22.4 s | $0.0081 |

**Decisions**

1. **Safety is solid on this set.** Route accuracy is 1.00 in all 10 configurations, across all 8 red flags, 4 near-misses and 5 adversarial prompts. The honest caveat is that the set is too easy to separate the arms: every arm scores 1.00. The next dataset iteration needs harder red flags (indirect phrasing, mixed languages).
2. **A/B 1: keep gpt-4.1 for the answer, but it's close.** gpt-4.1-mini halves cost ($0.0024 vs $0.0051) and latency (p50 10.6 s vs 17.6 s), with citation precision only 0.04 lower and identical routing/faithfulness. This is below our 0.05 threshold, so **by our own rule mini would be acceptable**. We keep gpt-4.1 because citation precision is the metric users feel, and with judge v2 the extra rewrites favour the stronger writer. Mini is the configured fallback, and the budget guard switches to it automatically.
3. **A/B 2: keep the reranker.** Without it citation precision drops 0.78 → 0.70 (the largest drop of any arm), and removing it saves ~5 s of p50 latency (17.6 → 12.7 s), because the cross-encoder runs on CPU under 4-way concurrency. The quality effect confirms the hypothesis; the latency cost is far above the 300 ms we hoped for. We optimised it: multi-query reranking went from 15 s to 3.8 s by re-ranking each query's own candidates only.
4. **A/B 3: keep multi-query retrieval.** Single-query retrieval missed the expected papers on one question (hit 0.93) and had lower key-point recall (0.93 vs 0.96). The miss is the motivating case: for "fasted cardio with PCOS" it retrieved only PCOS-exercise papers and answered "the research doesn't cover this". Its citation precision is slightly higher (0.80, within noise). Its p95 latency is 57 s vs 29 s, which is an outlier worth noting: 429 retries.
5. **Citation judge v2 is the clearest win.** Per-claim verification raised citation precision **0.78 → 0.93** with faithfulness unchanged. It triggers a rewrite on 43 % of answers (vs 5 %) and adds ~4 s p50 on evidence questions. Adopted as the default. This came from reading the round-1 failures, not from the original plan (see §6).
6. **Prompt v2 + loop vs v1:** prompt v1 without the loop got 0.73 citation precision. v2 without the loop got 0.73. v2 with the holistic loop got 0.78; v2 with the per-claim loop got 0.93. **The prompt alone didn't move citation precision; verification did.** v2's value shows elsewhere: evidence-strength tags, `[data]` personalisation, and refusing to overclaim, which these metrics only partly capture.
7. **Hyperparameters: keep T = 0.3, top_p = 1.0.** T = 0 is marginally better on citation precision (0.77 vs 0.75, within noise). T = 0.7 and top_p = 0.5 are worse (0.71 / 0.72), and T = 0.7 lost one retrieval hit. With judge v2 now catching citation drift, T = 0.3 keeps the personas' voices less robotic at no measurable quality cost. Hyperparameter differences are smaller than the effect of the architecture changes (reranker, judge).
8. **Cost per query:** ≈ $0.008 for research answers (≈ 7k tokens over 3–4 calls) and ≈ $0.0003 for red flags and blocks. The overall mean is $0.004–0.005. The pre-build estimate of $0.016 assumed a tool-planning call and longer contexts on every question; research questions usually skip the tools, so they came in about half of that.

**Final configuration (2026-09-25, 43 examples: per-claim judge + multi-query + all real-data fixes), run three times:**

| run | route | numeric | goal (incl. negative case) | faithfulness | citation precision | key-point recall | retrieval hit | p50 | cost / query |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 1.00 | 1.00 | 1.00 | 0.97 | 0.89 | 1.00 | 0.93 | 25 s | $0.0094 |
| 2 (`final_repeat`) | 1.00 | 1.00 | 1.00 | 0.99 | 0.95 | 0.96 | 0.93 | 19 s | $0.0069 |
| 3 (`final`, also logged in LangSmith as `bloom-final`) | 1.00 | 1.00 | 1.00 | 0.97 | 0.98 | 0.93 | 0.93 | 27 s | $0.0099 |

- **Run-to-run noise is about ±0.05** on citation precision (0.89–0.98 for identical configs; LLM generation *and* LLM judging vary). Differences smaller than that between single runs in the tables above are not conclusions.
- **The judge-v2 gain holds:** mean citation precision over the 3 final runs is 0.94 vs 0.78 for the round-1 baseline, well outside the noise band.
- **Latency and cost rose** (p50 19–27 s vs 18 s; ~$0.008–0.010 per query) because 37–44 % of answers now get a verified rewrite. That's the accepted quality-over-latency trade-off; tokens still stream, so users see text within a few seconds. The runs also hit OpenAI rate limits (new account tier), which inflates p95.
- **`ev09` regression found by these runs:** retrieval hit dropped to 0.93 because triage marked "how much activity is recommended?" as needing no research, so it was answered from memory, uncited. Fixed with a deterministic rule (general questions are always grounded) plus a unit test, and verified to cite the WHO guideline again. The fix landed after these three runs.

**What these metrics don't show:** answer *usefulness* or tone; whether a doctor would agree with the referral text; how things behave on real (messy) data; and judge self-preference (gpt-4.1 judging gpt-4.1). n = 14–23 per metric means a single example moves a score by 0.04–0.07.

## 6. Known failure modes and how we found them

- **Ungrounded general answers (`ev09`, final runs):** the triage LLM sometimes flags general guideline questions as `needs_research=false`, so they were answered from model memory without citations. Retrieval is now forced for every general (non-personal-data) question; `test_general_question_is_grounded_even_if_triage_says_no_research` guards it.
- **Unwanted goal proposals (`go03`, added 2026-09-25 after the result tables above were produced on 42 examples):** with real data, "which phase am I in and how should I adjust my training this week?" was triaged as `intent=goal` and interrupted for approval. Found in manual testing; the triage rule now requires an explicit request to set/save a goal, and `goal_proposed` scores the negative case.
- **Timezone drift in Apple Health:** the export stamps every record with the phone's timezone *at export time* (+05:00), so Apple workouts landed 4 h after the same Mywellness workouts, and cross-source dedupe silently failed. Fixed by normalising to Europe/Brussels (unit test).
- **The same event from several apps:** Mywellness mirrors Apple Watch walks/swims (66) and Withings weigh-ins (220 readings), and the Watch records Kinetix gym visits as separate workouts (55). `app/ingest/dedupe.py` now runs after every import (idempotent and order-independent; unit test), so "sessions per week" went from inflated to a true 3.0/week.
- **0 cycle days from a real Apple Health export:** newer iOS writes `HKCategoryValueVaginalBleeding*` instead of `HKCategoryValueMenstrualFlow*`. The parser skipped all 202 flow records until both labels were accepted (unit test added). Demo data can't catch format drift like this; only real exports do.

- **Lenient in-graph citation judge:** found by comparing the in-graph verdicts (95 % pass) with the offline `citation_precision` (0.78). Fixed with the per-claim judge v2 (0.93).
- **Wrong device for "my latest Tanita scan" (`da05`):** the agent answered with the latest Withings reading because `get_latest_metrics` hid the source. Fixed: the tool now returns the latest value per source, and 7-day deltas are computed within one source. `numeric_accuracy` went 0.88 → 1.00 in the next run.
- **Compound questions retrieving one facet only (`ev01`):** found in a live test before the eval. Fixed with triage-generated sub-queries + per-facet round-robin reranking (A/B 3).
- **Reading scale noise as progress:** a live goal answer celebrated "−1.5 % body fat in one week". Fixed with a trend-reading rule in the prompt and a noise-robust `weekly_avg_change_28d` in the trend tool (not yet re-evaluated: the account ran out of credits).

- **Irregular cycles:** for PCOS cycles (SD > 7 days or length > 35) the phase is a calendar guess. Found while building the demo data; now surfaced as `confidence: low` in the UI and prompt, and covered by a unit test.
- **Glued PDF text:** 6 of the 12 PDFs came out with 15–43 % unsplit words. Found by measuring the glued-word ratio per paper; fixed by glyph-gap reconstruction and guarded by a test.
- **Decorative citations:** the naive v1 prompt cited a passage on every sentence. This motivated the citation-check loop and the `citation_precision` metric. The `prompt_v1` arm quantifies it.
